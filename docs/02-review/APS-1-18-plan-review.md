## 1차 리뷰 (rev.1 대상) — REJECT

### CRITICAL-1 — "전수 확인" 주장이 거짓. 8곳 중 1곳만 다뤘다

rev.1의 M2 grep은 `"순환 의존성\|작업 시작 실패"`였다.
**이미 고치기로 정한 두 리터럴만 검색했다.** 결함 패턴을 검색하지 않았다.

패턴 기반(`grep -rnE "ticket_code \?\? [a-zA-Z]+\.id"`)으로 다시 돌린 결과 **8곳**:

| 행 | 함수 |
|---|---|
| workflow-service.ts:165 | `startWork` ← rev.1이 다룬 유일한 곳 |
| :246 :279 :296 :309 | `submitTest` (4곳) |
| :375 | `completeFix` |
| :489 | `approveReview` |
| :575 | `requestChanges` |

8곳 전부 `POST /api/workflow/:taskId` → `wrapAsync` → REST 응답이다.
rev.1대로 done 처리하면 **노출 표면의 87.5%가 그대로 남는다.**

> **아는 것만 재확인하고 모르는 것을 놓쳤다.**
> 완전성을 주장할 때는 리터럴이 아니라 **패턴**으로 검색해야 한다.

### CRITICAL-2 — 대체 리터럴이 스스로 상태 코드를 오염시켰다

rev.1은 `?? found.id`를 `?? '식별자 없음'`으로 바꾸려 했다.
`'식별자 없음'`에 **`없`**이 있고, `getErrorStatus`는 `'없'`을 보면 404를 낸다.

| 메시지 (내부 예외 = `잘못된 상태 전환: ...`) | 상태 |
|---|---|
| `작업 시작 실패 (<uuid>): {inner}` (현재) | **400** |
| `작업 시작 실패 (식별자 없음): {inner}` (rev.1 대체안) | **404** ← 오염 |

**"API 계약을 바꾸지 않는다"고 명시한 티켓의 수정이 그 불변식을 깼다.**
더 나쁜 것은 rev.1의 M1 표와 V2 절차가 `ticket_code`가 **non-null인 예시만** 써서
이 회귀를 **구조적으로 잡지 못했다**는 점이다.

리뷰어가 이 발생 경로도 조사해 줬다: `POST /api/tasks`(`api-server.ts:203-204`)가
`epic_id`를 강제하지 않고, epic-id-guard hook은 **MCP `create_task` 도구 전용**이라
REST 경로에 적용되지 않는다. `task-repo.ts`의 `create()`는 `epic_id`가 없으면
`ticket_code`를 null로 남긴다. → **REST로 만든 epic 없는 태스크는 영구히 null이다.**
이론적 케이스가 아니다.

### MAJOR
- **회귀 테스트 신설이 구현 단계에서 빠졌다.** Discovery §6이 완화책으로 요구했는데
  rev.1의 구현 단계에 없었다. 확인 결과 `hasCircularDependency`/`addDependency`
  테스트가 **전무**하다
- **`title` 트레이드오프 미검토.** rev.1은 "유일한 트레이드오프는 D2"라고 적었으나,
  UUID를 지우고 `title`(사용자 자유 입력)을 넣는 것도 트레이드오프다 —
  고객명·내부 URL·시스템명이 들어갈 수 있다.
  *완화 요인*: 같은 함수의 성공 경로(`:340`)가 **이미** title을 REST 응답으로 내보내고 있어
  새 노출 클래스를 만드는 것은 아니다

### MINOR
- 올바른 패턴 위치 인용이 `:157`이었으나 실제는 `:152-153`
- M1 표의 내부 예외 문구가 **실제 소스에서 복사한 것이 아니라 지어낸 예문**이었다
  (실제는 `task-service.ts:157` `잘못된 상태 전환: ...`). 결론(400)은 우연히 맞았으나,
  "실측"을 표방하는 표에 지어낸 문자열을 쓴 것은 이 플랜이 강조하는 원칙과 모순된다

## 2차 리뷰 (rev.2 대상) — FAIL (신규 MAJOR)

**CRITICAL 2건은 실제로 고쳐졌음을 리뷰어가 재현 확인했다.**

### 신규 MAJOR — 안전장치 자체가 검증 불가능했다

```
$ grep -c "^export " packages/mcp-server/src/api-server.ts   →  0
$ grep -n "^function getErrorStatus" .../api-server.ts       →  102:function getErrorStatus(...)
```

`api-server.ts`는 **export 문이 0개**인 Express 부트스트랩 스크립트다.
rev.2의 D5 테스트는 `getErrorStatus`를 import할 수 없고, 산출물 목록에 `api-server.ts`도 없었다.

| 실행자의 선택 | 결과 |
|---|---|
| 키워드 목록·상태 매핑을 테스트에 **재구현** | **자기 사본**을 검사. `api-server.ts`가 바뀌어도 테스트는 모른다 — **"검증했다고 주장했지만 실제로는 검증 안 됨"** |
| Express 앱을 띄워 HTTP 레벨 검증 | DB 필요 → D5가 명시한 "DB 불필요·flaky 회피" 목표와 충돌, `APS-1-19` 재노출 |

즉 *"V7이 핵심이다... 그 테스트가 실제로 결함을 잡는 것을 보인다"*는 rev.2의 주장이
**자기 완결적으로만 참**이었다. CRITICAL-2 재발을 막으려고 만든 장치가
그 자체로 착각이 될 구조였다.

### MINOR
- `workflowFailure`가 `Error`를 **반환**하는 설계 — 누군가 `throw`를 빠뜨리면
  **로그는 찍히는데 예외는 안 던져지는** 조용한 버그가 가능하고 TS가 잡지 못한다
- 8곳의 `action` 인자 문자열을 표로 명시하지 않아 "바이트 단위 동일" 주장을 실행자가 검증하기 어렵다

### 리뷰어가 확인해 준 것 (지적 아님 — 균일 처리의 근거)
- **`submitTest`의 4곳(:246/279/296/309)은 런타임에 상호 배타적**이다.
  하나가 throw하면 함수가 즉시 종료되므로 한 호출에서 최대 1곳만 실행된다
- **`ticket_code`는 상태 전환으로 변하지 않는 불변 필드**다
  (`taskRepo.updateStatus`가 `findById`로 재조회해 반환). 4곳의 값이 항상 동일하다
- **원래 8곳 중 어느 곳도 `console.error`가 없었다.** 즉 헬퍼는 로그를 **신설**하는 것이며
  Discovery의 "정보를 없애는 게 아니라 옮긴다" 원칙에 맞는 순개선이다
- **패턴 재스윕으로 추가 누락 없음 확인** — `notification-service.ts`의 `task.id` 4곳은
  내부 dedup 캐시 키(외부 노출 경로 없음), `github-service.ts:386`은 GitHub 이슈 본문의
  의도된 교차 참조 필드, `index.ts` 4곳은 호출자가 보낸 값
- rev.2의 신규 주장(M3의 epic_id 미강제, D2의 `:489` 재조회 간격, D3의 성공 경로 title 노출,
  M4 grep, `:152-153` 정정) **전부 사실 확인**

## 이 리뷰 3라운드가 막은 것 (기록)

코드는 아직 한 줄도 바뀌지 않았지만 리뷰가 다음을 사전에 차단했다.

1. **노출 표면의 87.5%를 남긴 채 "정리 완료"로 done 처리할 뻔했다**
2. **상태 코드를 지키겠다고 쓴 수정이 400을 404로 바꿀 뻔했다** — 그리고 내 검증 절차는
   그것을 구조적으로 잡지 못했다
3. **재발 방지 테스트가 자기 사본만 검사하는 착각 장치가 될 뻔했다**

셋 다 공통점이 있다 — **실행해서 확인하지 않고 텍스트만 읽었다.**
1번은 아는 리터럴만 grep했고, 2번은 non-null 예시만 대입했고, 3번은 import 가능성을 확인하지 않았다.
