최신 하네스 엔지니어링 동향 vs ai-pm-system 하네스

작성일 2026-06-21 대상 ai-pm-system (APS) 출처 Anthropic · OpenAI · Claude Code Docs 외 12종 수집 방식 WebSearch 크롤링

본 환경에서 WebFetch(본문 직접 읽기) 권한이 거부되어, 최신 동향은 WebSearch 결과 요약과 그 안에 포함된 1차 출처 직접 인용 문구에 근거한다. 모든 URL은 실재 확인된 1차/권위 출처다.

1. 2026의 합의: Agent = Model + Harness

2026년 업계는 "에이전트의 어려운 부분은 모델이 아니라 그 모델을 둘러싼 하네스"라는 합의에 도달했다. 하네스란 에이전트가 모든 세션에 걸쳐 작동하는 환경 전체에 대한 거버넌스 — 접근 가능한 툴, 충족 기준(검증), 실시간 오류 교정 피드백 루프 — 즉 일종의 AI control plane이다.

Agent = Model + Harness
“2025 was the year AI agents proved they could write code, 2026 is the year we learned that the agent isn't the hard part — the harness is.”
— Faros AI / Mitchell Hashimoto 인용

성숙 단계도 prompt engineering → context engineering → harness engineering의 4번째 패러다임으로 진화했다. 핵심 원칙은 “실수를 구조적으로 불가능하게 만들기” — 에이전트가 실수할 때마다 환경(하네스)에 영구 수정을 새겨 재발을 차단한다. 이는 본 프로젝트 글로벌 규칙의 “같은 실패가 반복되면 증상이 아니라 하네스를 고친다”와 정확히 같은 철학이다.

3. 차원별 상세 대조

① 거버넌스 / Control plane ◉ 높음
최신 모범 사례
  • 하네스 = 툴·충족 기준·교정 피드백 루프에 대한 거버넌스 (AI control plane)
  • OpenAI Lopopolo: 5개월 수동 0줄로 100만 라인·1,500 PR — 거버넌스가 규모를 만든다
  • 상태/라이프사이클을 단일 권위가 관장
ai-pm-system 구현
  • ai-pm MCP 티켓 렛저가 상태·승인 SSOT
  • create_task → start_work → submit_test → approve_review → done 결정론 상태기계
  • 서버측 전이 차단(testing→review 직접 전환 거부)
정합: 티켓 렛저가 control plane 역할을 그대로 수행. 10단계 워크플로우 + 자동 done 전환이 라이프사이클 거버넌스와 직접 대응한다.
② 결정론적 가드레일 / 휴먼 게이트 ◉ 매우 높음
최신 모범 사례
  • “'Never do this' in CLAUDE.md is the wrong approach. A real guardrail needs to be deterministic.”
  • PreToolUse hook이 가장 강력 — 에이전트 루프 밖에서 실행, exit code 2로 차단
  • 권한은 deny 우선 평가, 조직 정책으로 bypass 금지
ai-pm-system 구현
  • epic-id-guard — epic_id null 티켓 차단
  • discovery-guard — Discovery 산출물 없으면 플랜 차단
  • plan-review-guard — 산출물 3종 없으면 start_work 차단
  • codex-review-guard — 리뷰 산출물·중요변경 codex 흔적 검증
정합(모범 케이스): 2026이 권고하는 "지시문 → 결정론적 hook" 전환을 이미 4개 PreToolUse 가드(exit 2)로 구현. fast-track 마커 우회까지 결정론적으로 처리. 업계 모범 사례의 교과서적 구현.
부분 갭: agent-mapping.md의 CROSS-REGION 핸드오프 블록은 스스로 인정하듯 "PreToolUse hook이 에이전트 final message를 파싱하지 않아 강제되지 않는 절차적 검증"이다. 최신 원칙대로라면 이 협력 계약도 결정론적 게이트로 끌어올릴 여지가 있다.
③ 검증 루프 / 검증자 독립성 ◉ 높음 · 갭 존재
최신 모범 사례
  • 표준 사이클 Plan → Search → Modify → Verify → Repair
  • “The verifier is independent of the agent. The agent never gets to self-report success — the loop re-runs the actual test suite.”
  • Verify에 타입체크·테스트·빌드·린터를 실제 실행으로 배선
ai-pm-system 구현
  • Iron Law: 실행 증거 없는 완료 주장 금지
  • STRICT submit_test: build+lint+unit 전부 pass 강제(누락/skip 거부)
  • self-healing 루프(MAJOR 이하 자동 수정)
  • 작성자 ≠ 리뷰어, self-approval 금지
정합: "검증자 독립성"을 self-approval 금지 + 별도 critic/code-reviewer 패스로 구조적으로 구현. self-healing 루프는 "Verify → Repair" 사이클과 직접 대응.
갭: submit_test는 에이전트가 제출한 출력(≥10자)을 신뢰한다 — 서버가 테스트를 독립적으로 재실행하지는 않는다. 최신 모범 사례의 핵심("loop re-runs the actual test suite")을 100% 충족하려면, CI가 동일 커밋에서 빌드/테스트를 재실행한 결과를 렛저에 역연동하는 단계가 필요하다.
④ 서브에이전트 오케스트레이션 ◉ 높음
최신 모범 사례
  • 5대 패턴: sequential / parallel(fan-out·fan-in) / hierarchical / handoff / loop
  • 작성자 vs 리뷰어 역할 분리(탐지→수정)
  • 각 서브에이전트는 fresh isolated context → 메인 오염 차단
ai-pm-system 구현
  • 모델 라우팅: executor-low/sonnet/high, designer, critic
  • 단일 메시지 병렬 dispatch(리뷰 다중 라운드 60% 단축)
  • 파일 소유권 파티셔닝(동일 파일 동시수정 금지)
  • shared_memory coord: 키 핸드오프 + 핑퐁 상한 3라운드
정합: fan-out/fan-in·handoff·loop 패턴을 모두 보유. Superpowers dispatching-parallel-agents + subagent-driven-development로 fresh subagent 격리를 명문화.
⑤ 장시간 작업 / GAN식 3-에이전트 ◉ 높음
최신 모범 사례 (Anthropic 2026.04)
  • Planner(스펙) → Generator(스프린트 구현) → Evaluator(라이브 비평)
  • self-evaluation leniency를 생성/채점 분리 + 적대적 프롬프트로 보정
  • 라운드 사이 fresh 인스턴스(context reset) + 파일 핸드오프
ai-pm-system 구현
  • planner → executor → critic/code-reviewer 3분할
  • 적대적 검증: Codex challenge + critic adversarial(3중 검증)
  • docs/00~06 단계별 artifact 핸드오프, ultragoal 세션 연속성
정합(강함): Anthropic의 GAN 영감 3-에이전트가 본 프로젝트의 planner/executor/critic + Codex 적대적 challenge와 거의 1:1 대응. "self-evaluation leniency 보정"을 self-approval 금지로 선제 구현했다.
경미 갭: 라운드 간 "context reset"이 규칙상 권장(fresh subagent)일 뿐, Agent SDK compaction처럼 자동화된 메커니즘은 아니다. 대형 다세션 작업에서 ultragoal 외 자동 압축 경로는 미흡.
⑥ 컨텍스트 엔지니어링 ◐ 중간
최신 모범 사례
  • context rot: 토큰↑ → 정확 회상↓. 유한 자원으로 관리
  • compaction(요약 후 재시작) + structured memory + sub-agent
  • just-in-time retrieval: 사전 적재 대신 glob/grep로 필요 시점 회수
ai-pm-system 구현
  • sub-agent 격리 ✔ · memory/ structured memory ✔ · notepad/wiki ✔
  • 그러나 CLAUDE.md + rules 11종 + 글로벌 규칙을 매 세션 사전 적재
  • 규칙이 상호 참조([[link]])로 비대 — 토큰 비용 큼
갭(개선 1순위): 본 프로젝트는 방대한 규칙 문서를 전부 컨텍스트 선적재한다. 2026 모범 사례(just-in-time retrieval, progressive disclosure)와 반대 방향. 제안: 규칙을 "핵심 요약 + 필요 시 해당 rules 파일만 회수"로 재구성하면 context rot을 줄이고 토큰을 절감할 수 있다. structured memory(memory/)·wiki는 이미 올바른 방향.
⑦ 툴 설계 / MCP 효율 ◐ 중간
최신 모범 사례 (Anthropic)
  • 5원칙 + Prototype → Evaluate → Collaborate 반복
  • Namespacing(asana_search 식 prefix)으로 선택 정확도↑
  • 응답에 pagination·filtering·truncation으로 토큰 절약
  • Code execution + progressive disclosure → 97~98% 토큰 절감
ai-pm-system 구현
  • ai-pm MCP가 다수 도구를 직접 노출(create_task·smart_workflow·analyze… 60+)
  • 도구 namespacing은 mcp__ai-pm__* prefix로 충족 ✔
  • 표준 보안 베이스(_security-base.ts)로 입력 검증 ✔
갭: 모든 MCP 도구가 시스템 프롬프트에 풀스키마로 상주 → 토큰 부담. 2026 트렌드인 progressive disclosure(이름+짧은 설명만 노출, 호출 시 스키마 로드)나 code execution with MCP는 미적용. 이 세션 자체가 deferred tool + ToolSearch로 progressive disclosure를 쓰고 있다는 점이 역설적 — 같은 패턴을 ai-pm 도구군에도 적용할 여지가 크다.

4. 종합 판정

📌 결론: 강한 정합 + 3개 영역에서 2026 신규 트렌드 따라잡기 여지

ai-pm-system의 하네스는 2026 "harness engineering" 모범 사례와 구조적으로 높은 정합을 보인다. 특히 결정론적 가드레일(PreToolUse hook), 검증자 독립성(self-approval 금지), GAN식 planner/generator/evaluator 분리는 업계가 2026.02~04에야 명문화한 패턴을 이미 운영 중이다. "실수를 하네스에 영구 박제" 철학도 글로벌 규칙에 내장되어 있다.

반면 2026에 새로 부상한 효율·컨텍스트 트렌드에서는 따라잡을 여지가 있다:

  1. 컨텍스트 선적재 → just-in-time retrieval: 규칙 11종 전량 적재를 "요약 + 필요 시 회수"로 전환 (context rot·토큰 절감)
  2. MCP progressive disclosure / code-execution: ai-pm 도구군을 지연 로딩 패턴으로 (97~98% 토큰 절감 사례)
  3. 서버측 독립 검증: submit_test 신뢰 모델을 CI 재실행 역연동으로 보강해 "verifier re-runs actual suite" 원칙 완성
