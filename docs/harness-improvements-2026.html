①
컨텍스트 선적재 → Just-in-Time 회수
P1 노력: 중 리스크: 낮음

문제

2026 모범 사례(just-in-time retrieval, context rot 관리)는 "필요할 때 필요한 것만 회수"를 권한다. 반면 본 프로젝트는 매 세션 글로벌 CLAUDE.md + 프로젝트 CLAUDE.md + .claude/rules/* 11종을 통째로 컨텍스트에 선적재한다. 토큰이 늘수록 회상 정확도가 떨어지는 context rot을 스스로 유발한다.

현재 상태
  • 규칙 11종(continuous-execution, discovery-and-plan, code-review, fast-track …)이 전량 주입
  • 상호 [[link]] 참조로 비대, 대부분의 세션은 그중 1~2개만 실제 사용
  • fast-track 단순 변경에도 정식 워크플로우 규칙 전체가 적재됨
목표 상태
  • CLAUDE.md = 얇은 라우터(한 줄 요약 + 트리거 키워드 + 하드게이트 핵심만)
  • 상세 규칙은 트리거 시점에만 해당 파일 회수
  • 하드 게이트(hook)는 그대로 — 가드는 컨텍스트와 무관하게 항상 강제

개선안 — "Rule Router + on-demand load"

핵심 통찰: 강제(hook)와 안내(rules 본문)를 분리한다. 차단은 이미 PreToolUse hook이 결정론적으로 하므로, rules 본문을 컨텍스트에 상주시킬 필요가 없다. CLAUDE.md는 "언제 어떤 규칙을 읽어야 하는지"의 색인만 남긴다.

# CLAUDE.md (목표: 라우터화)
## 규칙 색인 (필요 시 해당 파일을 Read로 회수)
| 트리거 | 규칙 파일 | 한 줄 |
| 플랜 작성/Discovery | rules/discovery-and-plan.md | 3~5단계 절차 |
| 코드 리뷰 강도 분류 | rules/code-review.md     | 1/2/3중 검증 |
| 단순 변경            | rules/fast-track.md      | Discovery 생략 |
# → 본문은 주입하지 않음. 매칭 시점에 Read.

구현 단계

  1. 토큰 베이스라인 측정: 현재 CLAUDE.md+rules 적재 토큰을 token-counting으로 기록(개선 전후 비교 지표).
  2. 규칙 분류: 각 rules 파일을 "항상 필요(하드게이트 요약)" vs "조건부(상세 절차)"로 태깅.
  3. CLAUDE.md 라우터화: 본문 인라인 제거, 색인 표 + 트리거만 유지. 하드게이트 요약 5~7줄은 인라인 유지.
  4. 회수 경로 명시: "플랜 작성 직전 rules/discovery-and-plan.md를 Read" 식의 지시를 워크플로우 단계에 삽입(이미 단계별 참조 표기 존재 → 본문 의존만 제거).
  5. 회귀 점검: hook 차단·워크플로우 동작이 규칙 본문 부재에도 유지되는지 검증(가드는 파일 존재만 보지 본문 적재와 무관).
기대 효과: 매 세션 규칙 적재 토큰 대폭 절감(특히 fast-track·단순 질의 세션). context rot 완화로 장시간 작업 회상 정확도 개선. 코드 코어를 건드리지 않아 가장 안전 — 문서/정책 변경이라 fast-track 가능.
리스크/완화: 규칙을 "안 읽고 지나칠" 위험 → 하드게이트(hook)는 그대로라 정책 위반은 여전히 차단됨. 안내 누락 위험은 워크플로우 단계의 명시적 "지금 X 규칙 Read" 지시로 보완.
②
MCP Progressive Disclosure / Code-Execution
P2 노력: 중~높음 리스크: 중

문제

Anthropic Code execution with MCP는 도구를 풀스키마로 시스템 프롬프트에 상주시키는 대신, 이름+짧은 설명만 노출하고 호출 시점에 스키마를 로드(progressive disclosure)하여 측정상 97~98% 토큰 절감을 보고했다. 본 프로젝트의 ai-pm MCP는 60개 이상 도구를 직접 노출한다.

현재 상태
  • create_task·smart_workflow·analyze_*·research_* 등 60+ 도구 풀스키마 상주
  • 대부분 세션은 5~10개만 사용(create_task / smart_workflow / get_project_status 중심)
  • namespacing(mcp__ai-pm__*)은 이미 충족 ✔
목표 상태
  • 핵심 도구 소수만 상시 노출 + 나머지는 지연 로딩
  • 또는 도구를 코드 API로 노출해 호출 시점에만 스키마 적재
  • 이 Claude Code 세션의 ToolSearch 패턴과 동일 철학

개선안 — 2개 경로 (택1 또는 병행)

경로 A · Progressive Disclosure (점진 공개)

핵심 도구(create_task, smart_workflow, get_project_status 등 ~8개)만 상시 노출하고, 저빈도 도구는 메타 도구 뒤로 숨긴다.

// 상시 노출: 핵심 8종 + 디스커버리 도구 1종
ai_pm_list_capabilities()        // 이름+1줄 설명만 반환
ai_pm_load_tool("decompose_task")  // 호출 시 해당 스키마 로드
// → 60종 풀스키마 상주 제거, 필요 시점에만 적재

경로 B · Code Execution with MCP

도구를 호출 가능한 코드 API로 노출하고, 에이전트가 코드로 조합 호출. progressive disclosure(이름+60자 설명만 시스템 프롬프트)와 결합 시 최대 효과.

구현 단계

  1. 사용 빈도 계측: 활동 로그(get_project_activities)·텔레메트리로 도구별 호출 빈도 집계 → 핵심/저빈도 분류.
  2. 핵심 세트 확정: 워크플로우 필수 경로(create_task→smart_workflow→approve_review) 도구를 상시 노출로.
  3. 메타 도구 구현: packages/mcp-server에 list_capabilities + load_tool(또는 code-execution 래퍼) 추가.
  4. 클라이언트 호환 확인: Claude Code의 deferred-tool/ToolSearch와의 상호작용 검증(이중 지연 로딩 충돌 방지).
  5. 토큰 절감 측정: 시스템 프롬프트 도구 섹션 토큰 before/after 비교.
기대 효과: 도구 섹션 토큰 대폭 절감 + 도구 선택 정확도 향상(노출 표면 축소). namespacing은 이미 충족이라 출발점 양호.
리스크/완화: MCP 코어 변경 → 아키텍처 변경(3중 검증) 분류. 지연 로딩이 잘못되면 도구 호출 실패 → 핵심 세트는 항상 상시 노출로 안전망 확보. 단계적 롤아웃(저빈도 5종부터) 권장.
③
서버측 독립 검증 (CI 재실행 역연동)
P3 노력: 높음 리스크: 중~높음

문제

2026 검증 원칙의 핵심은 "The verifier is independent of the agent — the loop re-runs the actual test suite." 현재 submit_test는 에이전트가 제출한 출력 문자열(STRICT 모드: build+lint+unit 전부 pass, ≥10자)을 신뢰한다. 서버가 동일 커밋에서 테스트를 독립 재실행하지는 않는다 — 이론상 위조 가능.

현재 상태
  • submit_test가 에이전트 제출 출력을 신뢰(STRICT로 형식·pass 강제하나 재실행 아님)
  • Iron Law는 "실행 증거 동반"을 요구하나 절차적 신뢰
  • 이미 보유: link_pr_to_task, get_pr_status, sync_commit_progress
목표 상태
  • CI(GitHub Actions)가 동일 커밋에서 build/test/lint 독립 재실행
  • CI 결과(green)를 렛저에 역연동 → done 전환의 게이트
  • 에이전트 자기보고 ≠ 통과 판정의 단일 근거

개선안 — "CI를 독립 검증자로 승격"

에이전트의 submit_test는 1차 게이트로 유지하되, 최종 done 전환을 CI green에 종속시킨다. 이미 있는 PR 연동 도구를 검증 루프로 승격.

# GitHub Actions (.github/workflows/verify.yml)
on: [push, pull_request]
jobs:
  verify:
    steps:
      - run: pnpm -r build
      - run: pnpm --filter @ai-pm/mcp-server lint
      - run: pnpm --filter @ai-pm/mcp-server test
# → 통과 시 checks API가 green. 위조 불가(서버 외부 실행).
# 렛저 게이트: approve_review/done 전 CI 확인
get_pr_status(task_id) // GitHub checks 조회
// CI != green 이면 approve_review/done 거부 (신규 hook 또는 서버 가드)

구현 단계

  1. CI 워크플로우 구축: .github/workflows/verify.yml로 build+lint+test를 PR마다 재실행(이미 docs/ci-test-isolation.md 자산 존재 → 확장).
  2. PR↔태스크 연동 강제: link_pr_to_task를 워크플로우 8단계에 의무화.
  3. CI 게이트 추가: get_pr_status로 checks 조회 → green 아니면 done 전환 거부(서버측 또는 신규 PreToolUse hook).
  4. submit_test 역할 재정의: 에이전트 제출 = 1차(빠른 피드백), CI = 2차(권위) — 이중 검증 명문화.
  5. 회귀/우회 방지: CI 미설정 레포는 기존 동작 유지(opt-in), APS는 enforce.
기대 효과: "검증자 독립성" 원칙 100% 충족 — 위조 불가능한 외부 재실행이 최종 판정 근거. STRICT submit_test(에이전트 1차)와 CI(2차)의 이중 안전망. 직전 API_KEY enforce와 동일한 "opt-in 환경변수" 패턴으로 점진 도입 가능.
리스크/완화: CI/CD 인프라 변경 → 가장 큰 작업, 신규 인프라(3중 검증) 분류. CI 지연이 워크플로우 속도에 영향 → submit_test 1차 게이트는 유지해 즉시 피드백 보존, CI는 done 직전에만 차단. Render 배포 파이프라인과의 정합 필요.
④
라운드 간 자동 Compaction (장시간·다세션 작업)
P3 노력: 중 리스크: 낮~중

문제

Anthropic Harness design for long-running apps·Effective context engineering는 한계 임박 시 요약 후 새 윈도우 재시작(compaction)과 라운드 사이 fresh 인스턴스(context reset) + 파일 기반 핸드오프를 장시간 작업 표준 패턴으로 제시한다. 본 프로젝트는 fresh subagent를 규칙상 권장할 뿐, 컨텍스트 한계를 감지해 자동으로 압축·재시작하는 메커니즘은 없다. 대형 다세션 작업에서 ultragoal 외에 자동 압축 경로가 미흡하다.

현재 상태
  • fresh subagent 격리 ✔ (절차적 권장 — subagent-driven-development)
  • docs/00~06 단계별 artifact 핸드오프 ✔
  • ultragoal 세션 연속성 ✔ · notepad/wiki structured memory ✔
  • 그러나 한계 임박 감지 → 자동 요약 → 재시작 경로 부재 (수동·암묵적)
목표 상태
  • 컨텍스트 임계 도달 시 자동 compaction(요약 → 새 윈도우)
  • 라운드 종료 시 handoff artifact 자동 생성 → 다음 세션이 전체 히스토리 대신 요약 복원
  • ultragoal을 compaction 체크포인트와 통합

개선안 — "자동 compaction 체크포인트 + 파일 핸드오프"

핵심: 장시간 작업을 라운드 단위로 끊고, 각 라운드 끝에 "다음 세션이 읽을 요약 artifact"를 자동으로 남긴 뒤 fresh 인스턴스로 재시작한다. 전체 대화 히스토리 누적 대신 구조화된 요약만 승계하여 context rot·실패 시도 오염을 차단한다.

# 라운드 종료 → compaction 체크포인트 자동 생성
# .omc/ultragoal/<mission>/round-N-handoff.md (또는 docs/)
## 라운드 N 요약
- 완료: <무엇을 끝냈나>
- 진행 중 상태: <현재 위치>

# → 다음 fresh 세션은 전체 히스토리 X, 이 요약만 주입받아 복원
이 항목은 ①(규칙 선적재)과 다르다. ①은 세션 시작 시 정적 규칙의 적재 방식이고, ④는 장시간 작업 진행 중 동적 컨텍스트의 압축·승계다. 둘 다 context rot을 줄이지만 작동 시점이 다르다.

구현 단계

  1. compaction 트리거 기준 정의: 토큰 임계값 또는 라운드 경계(예: 한 Phase 완료) — 어느 시점에 압축할지.
  2. handoff 템플릿 표준화: .claude/templates/에 round-handoff 템플릿 추가(완료/진행/진입점/승계 계약 4필드).
  3. 네이티브 compaction 활용: Claude Code/Agent SDK가 제공하는 compaction을 장시간 워크플로우에 명시적으로 배선(요약 후 재시작).
  4. ultragoal 통합: 라운드 handoff를 ultragoal ledger의 진행 메모로 연결 — 단, 상태/승인 SSOT는 여전히 ai-pm MCP(이중관리 금지, omc-skills-integration.md 경계 준수).
  5. 재시작 주입 규칙: fresh subagent dispatch 시 "전체 히스토리 대신 직전 round-handoff만 주입" 지시를 agent-mapping.md에 명문화.
  6. 측정: 대형 작업의 세션당 토큰·완료율·재작업률 before/after.
기대 효과: 다세션 대형 작업(DB 마이그레이션·대규모 리팩터링)에서 context rot·실패 시도 누적 오염 차단. fresh 인스턴스 + 파일 핸드오프가 Anthropic 장시간 작업 모범 패턴과 정합. 기존 ultragoal·docs/ 자산을 재활용해 신규 인프라 부담 최소.
리스크/완화: 요약이 핵심 정보를 누락하면 다음 라운드가 맥락 손실 → handoff 템플릿의 "승계 계약" 필드를 필수화하고, 모호 시 직전 artifact를 추가 회수. ultragoal과 ai-pm 상태의 이중관리 금지 경계를 반드시 지킬 것(상태=ai-pm SSOT, ultragoal=진행 메모 한정).

종합 — 도입 순서와 분류

항목리뷰 분류티켓 시 워크플로우선행 의존
① 컨텍스트 JIT1중(문서/정책) → fast-track 가능티켓 → 구현 → 1중 리뷰없음 (즉시 착수)
② MCP Progressive Disclosure3중(아키텍처 변경)Discovery → Plan → Review → 3중 검증사용 빈도 계측 데이터
③ 서버측 독립 검증3중(신규 인프라)Discovery → Plan → Review → 3중 검증 + CodexCI 파이프라인, PR 연동
④ 자동 compaction2중(워크플로우·정책 + ultragoal 통합)Discovery(간략) → Plan → Review → 2중 검증handoff 템플릿, ultragoal 경계 준수
