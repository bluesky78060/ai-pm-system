# APS-1-25 Discovery — PROD_COMPUTE_HOSTS deny-list 견고화

**티켓**: APS-1-25 (P1, 3→1 상향) / **부모**: APS-1-17 / **작성**: 2026-08-24
**분류**: 사고 재발 방지 장치 + DB 데이터 무결성 → **3중 검증**. fast-track 금지
**Discovery 방식**: 자동 채움. 다만 §3에 **설계 대안이 갈리는 지점**이 있어 플랜에서 근거와 함께 확정한다.

## 1. 목표 (Why)

APS-1-32를 닫으면서 명시했다 — **"이 티켓이 done이 되어도 격리 복구 완료가 아니다.
APS-1-25까지 끝나야 그 말을 할 수 있다."** 그 약속을 이행하는 티켓이다.

APS-1-32는 `.env.test`가 셸의 `DATABASE_URL`을 확실히 이기게 만들고, 파일·키가 없으면
fail-fast 하게 했다. **그러나 `.env.test`가 존재하지만 프로덕션을 가리키도록 잘못 작성된
경우는 막지 못한다.** 그때 유일한 방어가 이 deny-list다.

### 현재 방어선의 한계 (실측)

```ts
// services.test.ts:11-15, context-service.test.ts:14-20 — 두 파일에 중복
const PROD_COMPUTE_HOSTS = [
	'ep-old-haze-aol2r7dt.c-2.ap-southeast-1.aws.neon.tech',
	'ep-old-haze-aol2r7dt-pooler.c-2.ap-southeast-1.aws.neon.tech',
];
```

**하드코딩된 엔드포인트 2개만 잡는다.** 그 외에는 전부 통과한다:

| `DATABASE_URL`이 가리키는 곳 | 결과 |
|---|---|
| 하드코딩된 그 compute | 차단 |
| **Neon이 재생성한 엔드포인트** | **통과** |
| **Render 프로덕션** | **통과** |
| **다른 프로젝트의 DB** | **통과** |

`context-service.test.ts:14-15`가 한계를 스스로 적어두고 있다 —
*"Update this list if Neon recreates the production endpoint."*
**사람이 갱신해야 유지되는 방어선은 갱신되지 않는다.**

## 2. 사용자 (Who)

- **로컬 개발자** — 사고가 실제로 났던 환경. `.env.test`를 손으로 만들며 오타·복붙 실수가 난다
- CI — `TEST_DATABASE_URL` secret이 잘못 설정되면 같은 위험. 사람이 확인할 수 없다

## 3. 범위 (What)

### 포함

1. **deny-list → allow-list 전환** — 모르는 호스트를 **기본 차단**한다.
   현재는 아는 것만 차단하고 모르면 통과시킨다. 방향이 반대다
2. **가드 중앙화** — 현재 두 파일에 **중복**돼 있다. 한 곳에서 관리한다
3. **`[DB Connection]` 로그에 호스트 추가** (`connection.ts:25`)

### 3-1. 설계 대안이 갈리는 지점 — 가드를 어디에 둘 것인가

| 위치 | 커버 범위 | 한계 |
|---|---|---|
| a. 각 테스트 파일 (현행) | 그 파일만 | 중복. 새 파일이 누락됨 |
| b. `vitest.config.ts` | 이 config를 쓰는 실행 전부 | `vitest --config other`로 우회 (APS-1-32 codex 지적) |
| c. `setupFiles` | 위와 동일 | 위와 동일 |
| d. **`getPool()` 자체** | **실제로 풀을 여는 모든 경로** | 프로덕션 코드에 테스트 전용 로직이 들어감 |

(d)가 유일하게 config 우회를 막는다. **가드는 하네스가 아니라 연결 지점에 있어야 한다.**
다만 프로덕션 코드에 테스트 분기를 넣는 것은 냄새이므로, 플랜에서 근거와 함께 확정한다.

### 3-2. allow-list를 무엇으로 정의할 것인가

가드가 "이 호스트는 테스트용"임을 어떻게 아는가. 자명하지 않다.

| 방식 | 문제 |
|---|---|
| 테스트 compute를 하드코딩 | deny-list와 같은 취약성. 방향만 뒤집힘 |
| `.env.test`에 명시적 opt-in 키 | 자기 인증이지만 **두 번의 고의적 행동**을 요구한다 |
| Neon API로 브랜치 확인 | 테스트 가드에 네트워크 의존은 과함 |

플랜에서 확정한다. 원칙은 **모르면 차단(fail-closed)**이다.

### 제외
- `.env.test` 로드·fail-fast → **APS-1-32** (완료)
- pre-commit 훅 버전 관리 편입 → **APS-1-21**
- 훅 정규식 결함 → **APS-1-22** / CI 이중화 → **APS-1-23**
- `connection.ts`의 TLS 설정 결함 → **APS-1-33** (같은 파일이므로 착수 시 조율)

## 4. 제약

- **STRICT 모드**: `submit_test`에 build + lint + unit 세 타입 모두 `pass`
- **가드가 너무 엄격하면 개발이 막힌다.** 새 개발자가 `.env.test`를 만들었는데 가드에 걸려
  이유를 모르면, 그 좌절이 가드를 지우는 동기가 된다. **에러 메시지에 해결법을 담아야 한다**
- **테스트를 실제로 돌려야 검증된다.** 가드가 정상 경로를 막지 않는지 확인 필요
- `connection.ts`는 **APS-1-33이 같은 파일을 대상**으로 한다. 충돌 주의
- 미커밋 변경이 누적돼 있다 (APS-1-32·APS-1-18). 리뷰 diff는 스냅샷 대조로 분리한다

## 5. 우선순위

1. **P1** allow-list 전환 — 이것이 티켓의 본체
2. **P1** 중앙화 — 중복 제거 없이는 다음 사람이 또 한 곳을 놓친다
3. **P2** `[DB Connection]` 호스트 로깅 — 비용 대비 관측 효과가 크다

## 6. 리스크

| 리스크 | 영향 | 완화 |
|---|---|---|
| **가드가 정상 개발을 막음** | 높음 | 에러 메시지에 해결법 명시. 정상 경로로 전체 테스트가 도는 것을 확인 |
| 프로덕션 코드에 테스트 로직 유입 (안 d) | 중간 | 플랜에서 근거 확정. 조건을 명확히(`process.env.VITEST`) 하고 프로덕션 경로에 영향 없음을 실측 |
| allow-list 자기 인증의 허술함 | 중간 | 완벽한 해법은 없다. **두 번의 고의적 행동**을 요구하는 것이 목표임을 문서에 명시 |
| `connection.ts`가 APS-1-33과 충돌 | 중간 | 로그 한 줄만 건드린다. TLS 블록은 손대지 않는다 |
| **가드를 넣었는데 실제로 차단하지 않음** | 높음 | **변이 검증 필수** — 프로덕션 호스트를 넣어 실제로 막히는 것을 보인다 |
| 테스트 flaky(APS-1-19)와 혼동 | 중간 | 실패 시 `duplicate key` 패턴인지 대조. 연속 실행 |

## 7. 검증

- **변이 검증(핵심)**: 재생성된 Neon 엔드포인트·Render 프로덕션·다른 프로젝트 DB를 가정한
  호스트로 각각 시도해 **수정 전에는 통과하고 수정 후에는 차단되는 것**을 실행으로 보인다.
  ⚠️ **실제 접속은 금지.** 문자열 판정 단계에서 차단되는 것만 확인하고,
  프로덕션 호스트에는 가짜 자격증명 또는 RFC 2606 `.invalid` 센티널을 쓴다
- 정상 경로(`ci-test` 브랜치)로 전체 테스트가 도는 것 확인
- `pnpm -r build` / `lint` / `test` 회귀 없음 (연속 실행)
- 3중 검증: code-reviewer + codex 독립 리뷰 + codex challenge

## 방향 확정

목표(모르는 호스트를 기본 차단)는 명확하다. **설계 대안 2개(§3-1 위치, §3-2 allow-list 정의)는
플랜에서 근거와 함께 확정**하고 리뷰에서 검증받는다. 사용자 결정이 필요한 항목은 없다.
