1. 2층 오케스트레이션 구조

두 시스템이 직교(orthogonal)하게 협력한다. 하나는 품질 가이드, 하나는 강제 게이트다.

Layer 1 · 조율 (품질 가이드)
OMC — oh-my-claudecode

멀티 에이전트 오케스트레이션 레이어. 전문 에이전트·모델 라우팅·스킬을 조율한다. 위임 규칙, 검증 원칙, 연속 실행을 정의하지만 차단하지는 않는다.

Layer 2 · 워크플로우 SSOT (강제 게이트)
ai-pm MCP — 티켓 워크플로우

모든 코드 변경의 단일 진실 공급원. 상태 전이(start_work → submit_test → approve_review → done)·리뷰 게이트·활동 로그를 관리한다. 서버가 비정상 전이를 차단한다.

Layer 3 · 보강 통합 (선택적)
Superpowers · gstack · OMC 신규 스킬

각 단계 디테일을 보강. Superpowers(브레인스토밍·플랜·검증), gstack(배포 자동화), wiki/ultragoal/autoresearch(지식·세션연속·지표최적화).

핵심 원칙: Hook(강제 차단)과 Superpowers(품질 가이드)는 직교한다. Hook이 통과시킨 호출에 대해서만 Superpowers가 품질을 보강한다.

2. 10단계 워크플로우

티켓 발행 → done 전환까지. 사용자는 3단계 "방향 확정"에서 한 번만 승인하면 된다.

  1. epic_id 확인 — get_project_status로 에픽 조회. null 절대 금지.
  2. 티켓 발행 — create_task(epic_id="...", title="...")
  3. Discovery Q&A — 7개 카테고리 문답 → docs/00-discovery/. 선택적 Gemini 리서치(docs/06-research/).
  4. 플랜 작성 — docs/01-plan/ (MD 기본 · HTML 선택). Discovery 산출물 선결 필수.
  5. 플랜 리뷰 — critic 독립 리뷰 + 메인 오케스트레이터 자체 검토 → docs/02-review/. 즉시 다음 단계 진행(사용자 승인 게이트 아님).
  6. 팀 에이전트 병렬 위임 — 파일 소유권 파티셔닝으로 동시 위임.
  7. 빌드/테스트 → 코드 리뷰 → smart_workflow — Iron Law 적용. submit_test → approve_review → 자동 done.
  8. PR 생성 — /ship (done 상태 확인 후에만).
  9. 머지/배포 — /land-and-deploy → Render 배포 + 헬스 체크.
  10. 배포 후 모니터링 — /canary → 콘솔 에러·성능 회귀·스크린샷 비교.
Fast-track: 1중 분류 단순 변경은 3~5단계(Discovery/플랜/플랜리뷰)를 생략할 수 있다. 8절 참조.

4. 리뷰 강도 3단계

변경의 위험도에 따라 리뷰어 수가 달라진다. approve_review 호출 전 적용.

강도적용 대상리뷰 구성
1중 UI 스타일·문구, 단일 함수 버그 수정, 리팩터링(동작 보존), 테스트/문서 변경 code-reviewer 1회
2중 외부 API 통합(인증 제외), 새 MCP 도구, 새 React 컴포넌트, 신규 서비스 클래스, 새 의존성 code-reviewer + security-reviewer 병렬
3중 인증/세션/암호화, DB 마이그레이션, 신규 인프라, 결제/금전, 권한 시스템 code-reviewer + security-reviewer(또는 codex review) + critic adversarial challenge
Self-healing 자동 루프: 1차 리뷰에서 MAJOR 이하만 발견되면 메인이 즉시 executor-high에 "수정 + 회귀 테스트" 위임 → 사용자 개입 없이 1라운드 내 자동 재검증.
예외(사용자 확인 필수): CRITICAL 발견 · 같은 라운드 MAJOR 3건 이상(설계 결함 의심) · 정책/범위 변경.

5. 병렬 실행 패턴

병렬화 가능 (적극 적용)

  • 코드 리뷰 다중 라운드 → 단일 메시지 병렬 dispatch
  • 레이어별 풀스택 → DB + API + UI 동시 위임
  • 빌드 + 테스트 + 린트 동시 실행
  • Phase 4 문서 → CLAUDE.md / rules / README 동시

순차 필수 (병렬 금지)

  • 동일 파일 동시 수정
  • 의존성 있는 작업(서비스 → 도구 등록)
  • request_changes → submit_test (상태 의존)

효과: 리뷰 라운드 60% 단축, 테스트+구현 병렬 시 50% 단축.

6. 연속 실행 원칙

티켓 발행 후 done까지 단계별 사용자 확인 없이 자율 진행한다.

3대 규칙

  • 단계 사이 확인 질문 금지 — "다음 단계로 진행할까요?" 금지
  • 암묵적 정지(silent stop) 금지 — 결과 요약만 출력하고 턴 종료 금지. 같은 응답에 다음 도구 호출 포함
  • 중단 시 전체 보고 의무 — 이슈 전체 목록·영향 범위·결정 사항 모두 명시
중단 허용 예외 (4가지만): ① BLOCKED(외부 의존성·권한·환경) ② 진짜 모호한 의사결정 ③ CRITICAL 발견 ④ self-healing 3회 실패. 그 외에는 같은 응답에서 다음 도구 호출로 이어간다.

8. Fast-track 단축

1중 분류 단순 변경에 한해 Discovery/플랜/플랜리뷰를 생략한다.

활성화 절차

  1. 티켓 발행 (priority 4 권장)
  2. 마커 생성: active-ticket + active-ticket-fasttrack (내용 일치 필수)
  3. 즉시 start_work (guard hook이 마커 감지 → 검증 생략)
  4. 구현 → 빌드 → 1중 리뷰 → approve_review

차단 케이스 (정식 워크플로우)

  • 인증/세션/암호화
  • DB 마이그레이션
  • 결제/권한 시스템
  • 외부 API 신규 통합 · 풀스택 변경

단축 효과: 약 20분 → 8분 (-60%). 산출물은 docs/03-code-review/만 필수.

10. 핵심 금지 사항

  • 티켓 없이 코드 변경 금지 / epic_id null 금지
  • Discovery 산출물 없이 플랜 작성 금지 / 플랜 리뷰 없이 구현 금지
  • self-approval 금지 — 작성자 본인이 승인 호출 금지(작성자 ≠ 리뷰어)
  • 중요 변경(P0/보안/아키텍처/DB/외부 통합) → Codex 리뷰 + Challenge 3중 검증 필수
  • Iron Law — 검증 명령 실제 실행 증거 없이 완료 주장 금지
  • smart_workflow done 이전 PR 생성/push 금지
  • 5단계 "메인 오케스트레이터 승인"을 사용자 승인 게이트로 오해 금지 — silent-stop 규정 적용

11. 에이전트 통신 · 조율 프로토콜

에이전트는 서로 직접 통신하지 않는다. 오케스트레이터 허브 + 공유 상태(blackboard) 경유의 간접 조율이다.

흔한 오해 교정: "에이전트들이 서로 메시지를 주고받으며 유기적으로 돈다"는 P2P 그림은 이 시스템에 맞지 않는다. 서브에이전트는 컨텍스트가 격리되어 서로를 볼 수 없다. 유기적 협력은 ① 메인 오케스트레이터(=Claude 본인)의 dispatch/통합과 ② 공유 상태를 통한 간접 핸드오프로 이루어진다. 이는 의도된 설계다 — 격리로 컨텍스트 오염을 막고, 파일 소유권 분리로 충돌을 막는다.

토폴로지: Hub-and-Spoke + Blackboard

동기화 패턴

Fan-out / Fan-in

  • Fan-out: 단일 메시지 multi tool_use로 독립 에이전트 동시 dispatch
  • Fan-in (barrier): 결과 전부 수신 후 메인이 통합·판정
  • 파일 소유권 파티셔닝으로 충돌 방지

핸드오프 / 재개

  • 핸드오프: 에이전트 final message → 메인 → 다음 에이전트(새 컨텍스트)에 전달
  • SendMessage: 기존 에이전트를 컨텍스트 유지한 채 재개
  • fork: 오케스트레이터 컨텍스트 상속한 분신

실제 흐름 예시 — 코드 리뷰 → self-healing

에이전트끼리 직접 말하지 않는다. 모두 메인 경유다.

  1. executor 구현 → final message "완료, 파일 X 수정"을 메인에 반환
  2. 메인이 diff를 code-reviewer에 dispatch (격리된 새 컨텍스트)
  3. code-reviewer "MAJOR 1건" 판정을 메인에 반환
  4. 메인이 self-healing 판단 → executor-high에 "수정 + 회귀 테스트" 위임
  5. 상태는 내내 ai-pm 티켓에 기록 — 다음 단계가 같은 task_id로 이어받음

조정·교정 메커니즘 — A가 B 영역을 건드려야 할 때

격리 때문에 A는 B에게 직접 말할 수 없다. 하지만 A의 결과(final message)에 "B 영역에 이렇게 했으면 좋겠다"는 권고를 실어 오케스트레이터에 올리면, 오케스트레이터가 중재자로서 B에 반영한다. 단 실시간 push가 아니라 A 종료 시점의 반환(pull)이며, 반영 여부는 오케스트레이터가 판단한다.

cross-region 조정의 3가지 경로

경로시점방식한계
사전 분해 (예방) dispatch 전 의존성 있는 작업은 순차 강제. B 먼저 실행 → 결과를 A 프롬프트에 주입 분해를 틀리면(의존성 무시 병렬화) 조정 자체가 불가
blackboard 읽기 (런타임) 실행 중 shared_memory/notepad/docs/ 비동기 읽기 이미 써둔 것만 봄. 실시간 협상 불가
권고 반환 → 재dispatch (사후 교정) A 종료 후 final message에 권고 → 오케스트레이터 중재 → B 재투입. SendMessage(B 재개)·structured output로 정밀화 라운드 추가. 상호 의존 시 핑퐁
self-healing이 이 패턴의 구현체: code-reviewer(A)가 "executor가 이 MAJOR를 고쳐야 함"을 결과로 반환 → 오케스트레이터가 executor-high(B)에 수정 요구를 담아 재dispatch. A가 B에게 직접 말한 게 아니라 중재를 거친 것이다.
핑퐁 비용 → 순차 강제의 이유: B를 고쳤더니 A도 같이 바뀌어야 하면 A를 다시 띄워야 한다(추가 라운드). A↔B 상호 의존이 강할수록 핑퐁이 늘어난다. 그래서 애초에 의존 방향을 한쪽으로 정리(B→A 순차)해 핑퐁을 없애는 것이 핵심이며, 이것이 agent-mapping.md "순차 필수 패턴(병렬 금지)"이 존재하는 이유다.
